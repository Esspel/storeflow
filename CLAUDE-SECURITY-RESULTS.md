## Report

**1 verified HIGH-severity finding:**

### **Hardcoded encryption key in secure storage** (`src/lib/secure-storage.ts:17`)

**Impact.** Any attacker who can read the source or compiled bundle learns the fixed AES-GCM key and can decrypt all users' session tokens from IndexedDB storage (or from any captured ciphertext), bypassing session protection.

**Where.** `src/lib/secure-storage.ts`, line 17, in the `getCryptoKey()` function.

**What.** The AES-GCM encryption key used to secure session tokens in IndexedDB is hardcoded as the literal string `"storeflow-crypto-key-2026"` in the source code (line 18). The `encryptToken()` and `decryptToken()` functions (lines 25, 40) call `getCryptoKey()`, so the same key protects every user's session token. Once the code is known, decryption is trivial.

**Exploit scenario.** An attacker with access to the source code (via public repository or code leak) extracts the hardcoded key and decrypts session tokens from users' IndexedDB storage, potentially gaining unauthorized access to user accounts and performing actions as legitimate users.

**Preconditions.** 1) Access to the source code or client-side bundle (public repository / deployed site). 2) Access to user's IndexedDB storage (via XSS or physical device access), or interception of ciphertext.

**Recommendation.** Replace the hardcoded literal with a key derived from a server-provided secret or environment variable at runtime. Never embed encryption keys in client source code. Use a per-installation key generated by the Web Cryptography API or retrieved from a secure server endpoint at application startup.

**CWE ID.** CWE-798 (Use of Hard-coded Cryptographic Key)

**Verification.** This finding received 3 TRUE_POSITIVE votes out of 3 panel voters (unanimous). The other candidate (SSRF/unauthorized SAP proxy) was refuted by the panel — 3/3 veriders voted FALSE_POSITIVE.
